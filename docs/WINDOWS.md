## 2. What was adapted, and why (minimal)

1. **`gl_loader.cpp` sits on `ps2r_host`, not `ps2r_platform`.** Twinsanity's `GlContext::Create` calls
   `ps2r::glwin::Load` directly from the SDL library; ours routes every context creator through
   `host::GlLoadEntryPoints` (host arm, `ps2r_host`), which is the loader's caller -- so the table must be
   one library lower or `ps2r_host` would depend on `ps2r_platform`. Same block, same comment, one target
   name changed (noted in the CMake comment).
2. **`GlLoadEntryPoints` wraps `glwin::Load`** with our resolver (`SDL_GL_GetProcAddress` + the 1/2/3/-1
   failure-value filter + `opengl32.dll` `GetProcAddress` fallback for the GL 1.1 names) and stays
   idempotent; the "N of M GL entry points are missing" refusal text is Twinsanity's. `GlGetProcAddress`
   (the `glTextureBarrierNV` probe) is unchanged.
3. **Toolchain / presets / scripts:** paths and names only (`nativeee` for `twinsanityevolved`, the shim in
   `tools/build/`, `-Disc/-Elf/-GamesDir` the way `build.ps1` already spells them, `build-windows-clang-cl-*`
   binary dirs so they never collide with the round-3 `build-windows-release`).
4. **The cross build on macOS** keeps round 3's `engine/platform/windows/toolchain_cross_macos.cmake`
   (Twinsanity's toolchain FATALs on a non-Windows host by design) and gets ONE new input:
   `-DPS2R_GLCOREARB_INCLUDE_DIR=<dir with GL/glcorearb.h + KHR/khrplatform.h>` -- the two Khronos
   headers the vcpkg `opengl-registry` port installs on a Windows host, fetched into
   `$WORK/winx/opengl-registry/include/` here.
